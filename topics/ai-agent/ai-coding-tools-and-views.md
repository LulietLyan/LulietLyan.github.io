## 省流

> 常见用法是把大模型放进编辑器或终端，做补全、解释、重构建议、测试草稿和文档草稿。代表形态包括 IDE 内嵌助手（如 Cursor、GitHub Copilot）、对话式聊天界面，以及可调用工具的 Coding Agent。它们提高的是起草与检索速度，不自动等于正确的设计、安全的变更或可合并的代码。
>
> 对 AI 编码的合理看法是：**加速草稿，不替代工程判断**。模型擅长局部模式匹配与样板生成，弱于完整把握未写入上下文的约束、隐性业务规则和线上风险。因此生成结果必须经过阅读、静态检查、测试和（必要时）人工审查；涉及权限、密钥、数据删除与并发正确性的改动，更不能“生成即合并”。
>
> 面试里不必堆工具名单。说清自己用过的形态、典型工作流（提问 → 生成 → 审读 → 验证），以及不交给模型独自决定的边界，比罗列产品名更有说服力。

## 常见工具形态

| 形态 | 做什么 | 典型局限 |
| --- | --- | --- |
| 补全 / 行内建议 | 根据光标附近代码续写 | 上下文窗口短，易与仓库其他约定冲突 |
| 对话式助手 | 问答、解释、改一小段 | 看不到未粘贴的代码与运行结果 |
| Coding Agent | 多步读文件、改文件、跑命令 | 仍可能误改、漏测、越权操作 |

具体产品会迭代改名，回答重点应放在**能力形态**，而不是背品牌列表。

## AI 编码适合什么、不适合什么

较适合：

- 样板代码、测试骨架、错误信息解读
- 在已有风格下的局部重构建议
- 把口头需求整理成检查清单或实现草案

需要谨慎：

- 跨模块架构决策与数据一致性方案
- 安全边界、权限模型、密钥与审计相关改动
- 性能敏感路径与并发协议
- 没有复现步骤或没有验收标准的“顺便修一下”

## 推荐工作方式

```text
明确目标与约束
  -> 让模型提出或生成草案
  -> 自己读 diff，核对边界条件
  -> 跑测试 / 类型检查 / 相关手工验证
  -> 再提交或继续追问
```

把模型当成速度快的结对对象：它负责起草，你负责定义完成标准与否决权。

## 简短收口

会用 AI 工具是加分项；会约束它、验证它、对结果负责，才是工程能力。工具会变，审查与测试纪律不应变。
