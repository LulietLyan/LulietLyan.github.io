## 省流

> 编译和解释描述的是程序实现与执行方式，不是语言不可改变的固有属性。编译器在执行前把一段程序整体转换成另一种表示，目标可以是机器码、字节码或中间表示；解释器则在运行时读取程序或字节码并执行对应操作。
>
> 传统 AOT 编译把源码提前生成本机机器码，运行时启动快、优化空间大，而且不需要逐条解释，但目标文件与平台相关，修改后要重新构建。解释执行通常跨平台和交互性好，开发反馈快，但运行时要持续做指令分派和动态检查，峰值性能往往较低。
>
> 现代实现多数是混合模式。Java 先把源码编译成 JVM 字节码，JVM 可以先解释，再把热点 JIT 编译成机器码；CPython 也会先把 `.py` 编译成字节码，再由字节码解释器执行；Go 通常 AOT 编译成本机代码，但仍带有 GC 和调度器等运行时。因此简单说“Java 是编译型、Python 是解释型”只能作为入门近似，完整答案必须说明中间表示和运行时。

## 编译和解释到底在区分什么？

关键区别是“转换工作何时发生、产生什么结果、由谁执行”：

```text
AOT：源码 -> 编译器 -> 本机机器码 -> CPU

字节码解释：源码 -> 字节码编译器 -> 字节码 -> 虚拟机逐条执行

JIT：源码/字节码 -> 运行时收集热点 -> 即时编译机器码 -> CPU
```

编译器的目标不一定是机器码。例如 Java 的 `javac` 和 CPython 的字节码编译器都属于编译器，只是输出交给虚拟机继续执行。

解释器内部本身也是一个已经编译成本机机器码的程序。它读取下一条 AST 或字节码指令，完成分派和运算，再继续下一条。

## 典型执行模式

### AOT 编译

Ahead-of-Time Compilation 在程序运行前生成目标平台代码。Go、C、C++ 和 Rust 的常见工具链采用这种方式。

优势：

- 启动时不需要等待热点编译，性能比较稳定。
- 编译器能做跨函数、死代码删除等全局优化。
- 可以交付独立可执行文件，生产环境不必保留源码。

代价：

- 产物通常绑定操作系统和 CPU 架构，需要交叉编译或分别构建。
- 构建时间更长，修改源码后必须重新编译。
- 缺少真实运行数据时，某些优化只能依赖静态推断或 PGO。

### 源码或 AST 解释

解释器可直接解析源码或 AST 并执行。实现简单、交互反馈直接，但高层节点的分派成本较高。现代通用语言较少在每次运行时从头逐字符解释整个源码，通常至少会先转成 AST 或字节码。

### 字节码虚拟机

字节码比源码更接近机器操作，又与具体 CPU 解耦。虚拟机可以验证、解释和缓存字节码。CPython 和 JVM 都有这层，但二者的优化策略、类型信息和运行时完全不同。

### JIT 编译

Just-in-Time Compilation 在程序运行过程中发现热点方法或循环，再编译为机器码。它能利用真实类型、分支概率和调用频率做推测优化；假设失效时还可能 Deoptimization 回到较通用的执行路径。

JIT 的代价包括预热时间、编译线程的 CPU、Code Cache 内存以及性能随运行阶段变化。它很适合长期运行的服务，不一定适合生命周期极短的命令行程序。

## Java、Python、Go 分别属于哪种？

### Java

```text
Java 源码 -> javac -> JVM 字节码 -> 解释器 / JIT -> 机器码
```

所以 Java 同时有编译和解释/JIT 阶段。字节码带来跨平台能力，具体 JVM 再针对当前机器优化。Java 也存在 AOT 和 Native Image 等实现方式，不能把语言永远等同于某一种执行器。

### Python

以 CPython 为例：

```text
Python 源码 -> 字节码 -> CPython 字节码解释器
```

导入模块时可能把字节码缓存为 `.pyc`，减少下次解析和编译成本，但 `.pyc` 不是直接由 CPU 执行的本机机器码。PyPy 等实现还可以使用 JIT，因此“Python 语言只能解释执行”也是错误的。

### Go

```text
Go 源码 -> 编译、链接 -> 本机可执行文件 -> CPU
```

Go 的主流工具链采用 AOT，但可执行文件内仍包含运行时，负责 GC、GMP 调度、栈增长、Map、Channel 和网络轮询。编译型语言并不等于没有 VM 概念、没有 Runtime 或没有动态行为。

## 性能差异来自哪里？

解释路径通常多出字节码取指、分派以及动态类型检查；AOT 机器码可直接执行，并有更多静态类型信息。JIT 则可能根据真实运行状态生成比静态编译更激进的专门代码。

但语言性能不能只由“编译/解释”判断：

- 算法和数据结构通常比执行模式更重要。
- Python 调用 NumPy 时，主要计算可能在已经编译的 C/Fortran/CUDA 中完成。
- AOT 程序仍可能被 GC、系统调用、缓存未命中和锁竞争限制。
- JIT 程序预热后可能很快，但短任务可能还没达到峰值就结束。

## 常见权衡

| 维度 | AOT 编译 | 解释/字节码执行 | JIT 混合模式 |
| --- | --- | --- | --- |
| 启动 | 通常快 | 通常直接，但要初始化解释器 | 早期可执行，热点编译需要预热 |
| 峰值性能 | 较高且稳定 | 通常较低 | 可能根据运行数据达到很高峰值 |
| 跨平台 | 通常需分别构建 | 有对应解释器即可 | 字节码跨平台，VM 适配平台 |
| 部署 | 可形成独立二进制 | 需要解释器和依赖环境 | 需要 VM，或额外做原生构建 |
| 动态性 | 静态优化更容易 | 运行时修改和交互更自然 | 在动态性与优化之间折中 |
| 故障定位 | 构建期可发现更多问题 | 更多问题推迟到运行时 | 还要理解编译层级和去优化 |

这些只是常见趋势，不是定律。静态/动态类型、强/弱类型、编译/解释是不同维度，不能混为一谈。

## 扩展问题

### 编译型语言一定更快吗？

不一定。AOT 通常减少运行时分派，但 JIT 可以利用真实 Profile 做专门优化，解释型语言也能把热点交给原生库。必须基于实际实现和负载比较。

### Python 有没有编译过程？

有。CPython 会把源码编译成字节码，再由解释器执行。平常说它是解释型语言，是因为用户通常不显式生成并直接运行本机可执行文件，主要执行仍由解释器完成。

### Java 到底是编译型还是解释型？

两者都有。源码先编译成字节码；JVM 可以解释字节码，也可以 JIT 编译热点代码。更准确的说法是“编译到字节码，再由虚拟机混合执行”。

### 静态类型就一定是编译型吗？

不是。类型检查时机和代码执行方式是正交的。静态类型语言可以由解释器执行，动态类型语言也可以 AOT 或 JIT 编译。
