## 省流

> TCP 连接是**全双工**的：每个方向都有独立的数据流与关闭语义。一方调用关闭，只表示“我这一侧不再发送”，并不自动表示对端也发完了。因此拆除连接时，每个方向通常各自发送一个 `FIN`，并由对端 `ACK` 确认，一共四个段，俗称四次挥手。
>
> 三次握手建立连接时，第二步的 `SYN+ACK` 可以把“确认对方 SYN”和“发出自己的 SYN”合并在一个段里，所以是三次。挥手阶段，被动关闭方往往还需要时间把剩余数据发完，不能总把对 `FIN` 的确认和自己的 `FIN` 立刻合并，因而常见仍是四次。
>
> 若被动关闭方在确认对方 `FIN` 的同时已经没有数据要发，也可以把 `ACK` 与自己的 `FIN` 合并，这时看起来会变成三次挥手；这是允许的优化，不改变“两个方向分别关闭”的本质。

## 四次挥手在做什么？

假设 A 主动关闭，B 被动关闭：

```text
1. A -> B  FIN          // A：我发完了
2. B -> A  ACK          // B：知道了，你这方向结束
   （此时 B 可能仍继续向 A 发送剩余数据）
3. B -> A  FIN          // B：我也发完了
4. A -> B  ACK          // A：确认 B 也结束
```

第 2 步之后进入半关闭：A 到 B 的发送已结束，B 到 A 仍可能有数据。这正是需要把“确认对方不再发送”和“自己不再发送”拆开的原因。

## 为什么握手是三次、挥手常是四次？

| 阶段 | 关键原因 |
| --- | --- |
| 三次握手 | 一方的 `ACK` 与自己的 `SYN` 可合并为 `SYN+ACK` |
| 四次挥手 | 两个方向的 `FIN` 通常独立；对 `FIN` 的 `ACK` 与自己的 `FIN` 不一定同时具备发送条件 |

全双工决定了“关发送”是单向动作；是否合并报文只影响段的个数，不改变双向关闭的语义。

## TIME_WAIT 为何存在（常被追问）

主动关闭方在发出最后一次 `ACK` 后会进入 `TIME_WAIT`，等待足够时间：

- 保证最后的 `ACK` 丢失时仍有机会处理重传的 `FIN`
- 让旧连接的重复报文在网络中过期，避免干扰复用同一四元组的新连接

这与“为什么四次”是相关但不同的问题：一个解释双向关闭，一个解释主动方延迟释放套接字。

## 简短收口

因为 TCP 全双工，每个方向都要单独结束发送；`FIN` 与对应 `ACK` 成对出现，默认就是四次。能合并时可以变成三次，但模型仍是两个方向各自关闭。
